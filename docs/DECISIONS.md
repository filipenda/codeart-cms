## 2026-11-25 (module registry and permissions)

Versions verified on Packagist: `spatie/laravel-permission` 8.5.0 (requires illuminate `^12.0|^13.0`, so Laravel 13 is supported), `composer/semver` 3.6.0.

- **M1. `spatie/laravel-permission` ^8.5 and `composer/semver` ^3.6 are `require`d by core.** Semver is needed at runtime to check module `requires` constraints (production has no dev tools).
- **M2. Core owns the permission tables migration** (copy of Spatie's schema, teams off, table names from `config/permission.php`) and the `modules` migration; both load through `loadMigrationsFrom`. Apps must not publish Spatie's own migration. Core registers Spatie's service provider itself.
- **M3. Manifest rules beyond the brief:** unknown fields are rejected; `name` is a lowercase slug; `package` must be `vendor/name`; permissions must start with `<name>.`; a menu item's `permission` must be one of the module's own (or `null` = visible to everyone); `migrations` is optional and must be a relative path without `..`; `description` is required. `requires`, `permissions`, `menu`, `migrations`, `license` are optional.
- **M4. Discovery never throws for one bad module:** invalid manifests, package/name mismatches and duplicate names are collected as "problems" and shown by `module:list`; other modules keep working.
- **M5. Conventions inside a module package:** routes in `routes/web.php` (loaded with the `web` middleware), views in `resources/views` (namespace = module name), migrations at the manifest's path. Core loads them only for enabled modules. API/console routes are not covered yet. Routes are skipped if the app's route cache exists (an app that caches routes must re-run `route:cache` after enabling/disabling).
- **M6. Enabled-list cache** is one forever-key (`codeart.modules.enabled`) in the default cache store, forgotten on enable/disable, never written while the database is not ready. If the cache store itself fails (e.g. database cache table missing at install), it falls back to the database, then to "nothing enabled".
- **M7. Module boot happens in an `$app->booted()` callback** of core's provider, so every other provider is registered first. Enabling at runtime boots the module immediately (so its own `ModuleEnabled` listener receives the event it caused).
- **M8. Enable/disable are idempotent:** enabling an enabled module (or disabling a disabled one) does nothing and the command says so; it is not an error. Re-enabling never repeats migrations (Laravel's `migrations` table) and never duplicates permissions.
- **M9. Version constraints on `requires` are checked against the installed version, but `dev-*` / `*-dev` installs (path repositories, the monorepo) skip the check**, because they have no comparable version.
- **M10. Permissions are created for the default guard (`auth.defaults.guard`) and not assigned to any role.** `super-admin` passes via `Gate::before`; `admin` and `editor` get module permissions explicitly (future admin screen). Disabling never removes permissions.
- **M11. `disable` of a module whose package vanished from `vendor/`** still flips the record to disabled (so a site can recover) but fires no `ModuleDisabled` event (no manifest to announce). `module:list` flags such modules.
- **M12. `module:enable`/`disable` are CLI-only and have no authorization check;** whoever has a shell is trusted. The `manage-modules` Gate (super-admin only, also via `Gate::define` so `admin` is denied explicitly) is for the future admin screen.
- **M13. Roles come from an action `CreateDefaultRoles`,** exposed as `php artisan codeart:roles` and `RolesSeeder` (not wired into the app's `DatabaseSeeder`; the app calls it where it wants).
- **M14. Example module** lives in `packages/modules/example`; the starter pulls it with a second path repository (`../../packages/modules/*`) and `codeart/module-example: @dev`. Its routes return JSON (no views, so no colors involved). Its listener seeds one row when the module is enabled.
- **M15. Tests:** core tests use fixture modules (`tests/Fixtures/modules`) through a fake discovery, the array cache, and `migrate:fresh` before each module test (enabling runs DDL, so transaction-based `RefreshDatabase` cannot be used). The starter's example-module tests live in `tests/Modules` for the same reason. Test stub user = `Tests\Support\StubUser` with `HasRoles`; the starter's real `User` got the trait.
- **M16. Release rules** documented in CONTRIBUTING.md (full), CLAUDE.md (short) and ARCHITECTURE.md; no CI/release automation added (not asked).

## 2026-11-25 (content translations)

Verified on Packagist: `astrotomic/laravel-translatable` 11.17.2 (2026-10-28) supports Laravel 13 (`illuminate/* ^9 ... ^13`) and is maintained. No new dependency was added.

- **T1. Own small trait instead of Astrotomic.** Astrotomic fits the storage model, but we need a per-locale fallback chain (sr-Cyrl -> sr, en -> sr; Astrotomic has one fallback locale), a derived locale with `manual_fields` logic hooked into every save, and unique-per-locale slugs. That means overriding its fallback, its save path and its attribute handling, i.e. more glue than the ~200 lines of the trait, plus coupling to its internals and a third-party release cycle for a core feature. Same table layout as Astrotomic (`<model>_translations`, `locale` column), so migrating to it later stays possible.
- **T2. Config shape:** `codeart.locales` = `default`, `enabled`, `fallbacks`, `available` (per locale `label`, `script`, `manual` or `derived_from` + `transliterator` class). The default locale is always appended to every chain; chains only contain enabled locales. Content locale = `app()->getLocale()` if enabled, else the default. Config arrays are merged shallowly by Laravel, so an app overriding `locales` replaces the whole block.
- **T3. Writes go through `setTranslation()`** (saves immediately, in a transaction, model must exist). Attribute reads (`$item->title`) are current-locale with fallback; assigning `$item->title = ...` is not translated (no magic setter). Fallback is per translation row, not per attribute (an `en` row with an empty description does not borrow the `sr` description).
- **T4. Slug rules:** `Slug::make` = Laravel `Str::slug` after `đ -> dj` (Serbian convention), empty result becomes `item`. A missing slug is generated from `title` and made unique per locale (`-2`, `-3`). An existing slug is kept when the title changes (stable URLs). An explicit slug is normalised and uniqueness-checked too. `sr-Cyrl` slug is always copied from `sr`; if `sr` is missing, one is generated from the Cyrillic title.
- **T5. `resetToAutomatic($locale, ...$attributes)`** with no attributes resets all; it regenerates from the source (nothing happens if the source is missing). Saving a derived locale only touches the attributes passed; `slug` passed to a derived locale is ignored.
- **T6. Transliterator rules:** protected spans (tags, script/style, entities, URLs, e-mails, `{{ }}`, `{!! !!}`, `{name}`, `:name` not preceded by a letter or digit, printf-style `%s %1$d %.2f`) are split out by one regex and everything else goes through a `strtr` table (longest key first, so digraphs win). Invalid UTF-8 is returned unchanged. Known limitation (injekcija) documented in `docs/modules.md`.
- **T7. Example module:** its `create_example_items_table` migration was edited in place (never released, `title` moved to `example_item_translations`) instead of adding a second migration. The welcome item is seeded in `sr` and `en`. `ExampleItemFactory` (in `database/factories`, autoloaded by the module) creates an `sr` translation; `translated($locale, [...])` adds more.
- **T8. Translation tables have no timestamps;** `title` is indexed in the example migration. Collation follows the connection (`utf8mb4_unicode_ci`); a test asserts utf8mb4 and a Cyrillic round trip. Note: with `_ci` accent-insensitive collation `c`/`č` compare equal in searches; slugs are ASCII so the unique index is unaffected.
- **T9. PHPStan:** `trait.unused` ignored for `Translatable` (it is used by other packages/tests, not by core's `src`).
- **T10. Starter `composer.lock`** was refreshed (`composer update codeart/module-example`) because the module's autoload gained the factories namespace; the lock's dev-branch version string changed with the branch name.

## 2026-11-25 (settings in the database)

No new dependency (Laravel cache, encryption, validator and spatie/laravel-permission already cover it).

- **S1. Two tables:** `settings` (`key`, `group`, `locale` default `'*'`, JSON `value`, unique `(key, locale)`) and `settings_locks` (one row per locked key). A lock covers all locales of a key, so it does not belong on a per-locale row.
- **S2. One cache entry** (`codeart.settings`, forever) holds all values and locks; every write forgets it. Values are cached as stored, so secrets stay encrypted in the cache. Nothing is cached while the tables are missing, so install-time reads fall back to defaults and the next request retries. A per-request memo avoids repeated cache reads.
- **S3. Definitions:** `permission: null` means super-admin only. `default` may be a Closure so config stays the default source (config can change after boot). Module definitions are registered once by the provider and filtered by "module enabled" on every lookup, so disabling hides them immediately (also in the same process) and values survive. Duplicate keys throw.
- **S4. Writing:** value is cast to the type first (CLI strings welcome: `"7"`, `"true"`), then Laravel rules run. `null` removes the stored value (default applies). Cross-field rules are a `check` closure that sees the final state; `Settings::setMany` writes several keys atomically so e.g. a new default locale and the new enabled list are validated together. Errors never contain the value (secrets).
- **S5. Translatable settings** read the requested locale, then the default locale, then the definition default. A locale on a non-translatable setting is an error.
- **S6. Permissions:** `settings.appearance` is created by `CreateDefaultRoles` and given to `admin` only when it is first created, so a later revoke is not undone by re-running `codeart:roles`. Locale settings use `settings.appearance` as asked. Manager order: permission first, then lock (an unauthorized user does not learn the lock state). `canUpdate()` exists for the future UI.
- **S7. Secrets:** `Crypt::encryptString(json)`; an undecryptable value (changed `APP_KEY`) reads as unset. `settings:set` asks for a secret without echo when no value is given (a value on the command line lands in shell history). `masked()` returns `********`, or null when unset.
- **S8. Theme:** config `theme` keys are now `primary, secondary, mode, logo_light, logo_dark, favicon` (`default_mode`/`logo` renamed). `theme_defaults` stays = what tokens.css defines (no override when equal). `ThemeSettings` now takes `Settings` in its constructor. Mode `auto` renders `data-theme="auto"`; tokens.css got a `@media (prefers-color-scheme: dark)` block for `:root[data-theme="auto"]` (a copy of the dark values, colors stay only in tokens.css) and the generated `<style>` repeats custom dark overrides inside the same media query. The `<html>` tag belongs to the client's layout: core offers `partials/theme-attributes`.
- **S9. Images:** the real type is decided by `getimagesize` AND libmagic (both must say png/jpg/webp); the stored extension comes from the detected type, the name is random (40 chars), defaults 2 MB and 4096x4096 (`codeart.branding`), disk `public`, folder `branding`. Files are not re-encoded (a valid image with trailing junk is kept; it is served as an image, never executed). The old file is deleted only if it lives in the branding folder. **SVG is rejected:** it can contain scripts and external references, sanitizing needs a dedicated library and review; revisit with a sanitizer if clients ask.
- **S10. Locales:** `Locales` reads `default/enabled/fallbacks` through `Settings` (constructor now `Locales(Settings, array $config)`); `available` (labels, scripts, transliterators) stays in config because it describes code, not choices. Rules: default is enabled; enabled is a non-empty list of known locales; any enabled locale with `derived_from` needs its source enabled (this covers `sr-Cyrl` needs `sr`); fallbacks map known locales to lists of known locales.
- **S11. Security defaults (not enforced):** 2FA off, required roles `super-admin, admin`; password min 10 (8-128), mixed case and number required, symbol not; session 120 min (5-43200); login 5 attempts (1-100), 15 min lockout (1-1440); activity log 90 days (7-3650).
- **S12. CLI:** `settings:list [--group]`, `get`, `set` (typed; JSON for lists; `null` resets), `lock`, `unlock`. Validation problems are printed as one-line errors with exit code 1.
- **S13. Tests:** settings tests run `migrate:fresh` per test (like module tests); the `alpha` fixture module registers `alpha.greeting` to test module-owned definitions.

## 2026-11-25 (authentication backend)

New dependencies, newest stable checked with Composer on 2026-11-25: `laravel/fortify` 1.44.0 (requires Laravel 13; pulls `pragmarx/google2fa`, `bacon/bacon-qr-code`, `laravel/passkeys`) and `spatie/laravel-activitylog` 5.1.5 (Laravel 12/13, PHP 8.4). Larastan, Pint and Pest versions unchanged.

- **A1. Fortify, headless.** It supports Laravel 13, so no replacement was written. `Fortify::ignoreRoutes()` plus our own registration of its `routes.php` in `boot()`, because the admin path is a setting and settings are not reliably readable in `register()` (the test harness showed the database default is not final there). Fortify's views stay off (`codeart.auth.views`); route names are Fortify's own (`login.store`, `register.store`, ...). Fortify's `passkeys` dependency comes along but is unused.
- **A2. spatie/laravel-activitylog, thin wrapper.** The alternative was our own table, model and prune query (about 80 lines, but also our own morph handling and a model nobody else knows). Spatie gives the model, morph relations and a stable table; our `ActivityLog::record()` (about 60 lines) adds ip and user agent, strips secret-looking keys and never throws. The table is created by core's own migration (published stub plus `ip_address`, `user_agent`). The spatie model events (`LogsActivity`) are not used.
- **A3. Guard and roles.** Guard `admin`, also the default guard when the app still has `web` (the database session handler records user ids through the default guard). Roles and permissions live under guard name `admin` (the trait's `guardName()`); `CreateDefaultRoles` and `EnableModule` use it instead of `auth.defaults.guard` (supersedes M10's wording). New role `member`. Permissions are granted to roles only when first created (a later revoke sticks).
- **A4. Role ranks** in `config('codeart.auth.role_rank')` (super-admin 100, admin 50, editor 10, member 0, unknown roles 98 so only a super-admin hands them out). One rule serves invitations, role changes, deactivation and the policy: nobody above their own rank, only a super-admin touches a super-admin, nobody deactivates themselves. A command-line actor counts as super-admin (it has shell access).
- **A5. `admin.access` semantics.** Approval and e-mail verification are checked against the registration settings (`require_approval`, `require_email_verification`), also for users created otherwise; existing users get `approved_at = now` in the migration and `user:create`/invitations set approved and verified, so turning a setting on never locks out existing staff. Order of reasons: inactive, unapproved, unverified, forbidden, two-factor. A deactivated user cannot sign in at all (identical error); unapproved/unverified users can sign in (they must, to verify) but get 403 on admin routes.
- **A6. Two-factor.** Defaults corrected to `required` for `super-admin` and `admin`. Fortify's confirm step and password confirmation are on. Mode `off` blocks starting setup (403) but users who already have 2FA are still challenged (otherwise turning the mode off would be a bypass). While required-and-missing, only `two-factor.*`, `logout`, `admin.session` and password-confirm routes pass.
- **A7. No enumeration.** Login: identical 422 for unknown, wrong password and inactive, one hash check even for unknown e-mails. Reset link: identical 200 for known, unknown and throttled; mail sent after the response (`terminating`) so response time does not tell either. Reset: identical 422 for wrong e-mail and wrong token. Not covered: registration reveals an existing e-mail (validation), a known trade-off of public registration (documented).
- **A8. Login throttle** by e-mail + IP with `security.login.max_attempts` and `decay_minutes`, as a subclass of Fortify's `LoginRateLimiter` (so the `Lockout` event and 429 still work); Fortify's own route throttle for login is turned off to avoid two counters. Remember duration is applied per request by a middleware on the Fortify routes (also covers the 2FA challenge).
- **A9. Sessions.** Database driver forced when the app has `file` or `cookie`; `session.lifetime` set from the setting at boot. Own-session list/revoke is a service plus thin JSON routes (`admin.sessions.*`); "log out other devices" deletes the other rows and rotates the remember token (needs the password). A password reset or deactivation deletes all of the user's sessions; a password change deletes the others.
- **A10. Passwords.** `PasswordRules` rebuilds the Laravel `Password` rule from settings on every use. The breached check is Laravel's `uncompromised()` wrapped so that any exception (network, HTTP error) lets the password through.
- **A11. Invitations.** Token: 64 random characters, stored as SHA-256. The link is a signed route (path holds the token), and the row is checked again (expiry, single use, `lockForUpdate`). A new invitation replaces an open one for the same address. Accepting re-checks that the inviter can still hand out the roles. Unknown/used/expired answer the same 410. Invitation mail is sent at once (errors visible), the others after the response.
- **A12. Registration.** The route always exists; a middleware answers 404 while `auth.registration.enabled` is off, so toggling needs no route changes. `default_role` may not be `super-admin` or `admin` (setting rule). Pending users are `is_active=false` (cannot sign in later) but Fortify signs them in right after registering so they can verify. Throttle 5 per hour per IP. Bot protection: honeypot field `company_website` and an encrypted timestamp `form_token` (APP_KEY), min age `auth.registration.min_seconds`, max age 24 h; every failure gives the generic message.
- **A13. Mail.** Settings `mail.*` override `.env` only for stored values; applied in boot, safe without tables. `ssl` maps to scheme `smtps`, `tls` to `smtp` (STARTTLS when offered), `none` to plain `smtp`. One template for all mails; colors from `ThemeSettings::emailPalette()` (new, derived from the theme settings and `theme_base`), so `check:colors` and its allow-list stay untouched. The mail locale is the user's `locale` if enabled, else the app locale (invitations to people without an account use the app locale).
- **A14. Language files.** Authored in `sr` and `en`, `sr-Cyrl` generated and committed (`lang:transliterate`, `--check` in a test). Because Laravel 13 ships no lang files, `auth.*`, `passwords.*` and `validation.*` would show raw keys; core's `framework.php` is used through the translator's missing-key hook only when neither the app nor a fallback locale has the key (an app's own translation always wins). Caveat: an app that published English files shows English there for `sr` users until it adds `sr` files.
- **A15. Tests** for auth live in `packages/core/tests/Auth` with their own base class (Laravel's users/sessions migration copied to `tests/Fixtures/migrations`, because the other suites create their own minimal `users` table). Sessions are exercised with a carried session id (the test client keeps no cookies). Settings rows are cleared after each auth test because the admin path is read at boot.
- **A16. Not done / later.** Passkeys, per-user notification preferences, "approve" and user management screens, a pending-registrations query helper, automatic re-sending of invitations, and Turnstile (explicitly out of scope).

## 2026-11-27 (admin UI step 3: data table)

- **TB1. Exactly one page per request.** A list loads one page (default 25, hard maximum 100 per page); never all rows. `per_page` is clamped to 1..100 (non-numbers and values below 1 give the default), `page` to 1..100,000,000, and a page past the last one redirects to the last page (to page 1 for an empty result).
- **TB2. Every column sorts and filters; the exact count is the default.** We impose no whitelist: every declared column sorts, searches and filters unless it opts out, and the total is a real `count(*)`. A table is optimized individually (an index, a cached or estimated count) only after a measurement shows it is slow. Sorting and filtering use only the column expressions the developer declared, never request input, with the primary key as a tie-breaker so pages never repeat or lose rows.
- **TB3. Bulk actions and exports run in chunks.** Bulk uses `chunkById` (500), export streams chunks of 1000 (keyset on the key when ordered by it, offsets otherwise); no code path loads all rows or all ids. "Select all results" sends the filter (`scope=filter` plus the query string), not ids; ticked rows are at most one page (100 ids).
- **TB4. No N+1.** A table declares its eager loads (`with`), applied to the page, to bulk chunks and to export chunks. A test renders 10 and 100 rows and requires the same number of queries (count, page, relations, permissions).
- **TB5. Queue policy for bulk actions.** Up to `queue_limit` rows (1000) a bulk action runs inside the request. Above it: if `queue.default` is a real driver (not `sync`/`null`; the database queue counts, the scheduler works it off) it dispatches `RunBulkActionJob`, which rebuilds the table from the registry key, re-checks the permission and runs the same chunked loop; if there is no queue (typical shared hosting) it still runs in chunks inside the request up to `hard_cap` (10,000) and above that refuses with "too many rows, narrow the filter". Reason: a request that silently does nothing, or one that times out half done, is worse than a clear message.
- **TB6. State lives in the query string.** `q`, `sort`, `dir`, `filter[...]`, `per_page`, `page`; the toolbar is a GET form, sorting and paging are links, so lists are linkable and work without JavaScript. Defaults are left out of URLs. Alpine only debounces the search (400 ms), submits on filter change and counts the selection.
- **TB7. Tables are registered by key.** Bulk and export are generic endpoints (`codeart.tables.bulk`, `codeart.tables.export`) that rebuild the table from `TableRegistry`; a class name never comes from the request. The key is the `DataTable` id. A table that is not registered still renders, without checkbox column, bulk bar or export. The bulk confirm text is shown in the confirm dialog when JS runs; the server does not depend on it (see TB11).
- **TB8. Permissions twice.** Row actions, bulk actions and export are hidden when the permission is missing and checked again on the server (403 for bulk and export; the queued job checks again). A row action only links to a module route, which must authorize the request itself.
- **TB9. CSV rules.** UTF-8 with BOM (Excel), comma separated, `\r\n` lines, header from the column labels, only exportable columns, current filter and sort, cells that start with `= + - @`, tab or CR prefixed with `'` (numbers are not touched), refused above `export.max_rows` (500,000) instead of silently truncated. Excel `.xlsx` is a later task.
- **TB10. Benchmark approach.** `codeart:bench:table` (not in CI) fills `codeart_bench_items` from MariaDB's `seq_1_to_N` (`INSERT ... SELECT`), adds the indexes afterwards (`status`, `category_id`, `created_at`; `title` and `created_by` stay unindexed on purpose), runs the real `DataTable::resolve` and `CsvExporter::write`, prints best and median of 3 runs and drops the table in `finally`. It reports, it does not optimize. Result of the first run (1,000,000 rows, DDEV, MariaDB 12.3): see the report of this step; the three operations above 1 s were the multi-column `LIKE` search, search + filter + sort combined, and the 100,000 row CSV export (about 3.3 s).
- **TB11. Destructive actions are confirmed on the server.** `window.confirm` protected nothing without JavaScript, so a destructive action (a `BulkAction::destructive(...)` or any non-GET row action / `<x-codeart::confirm>` button) never runs unless the request carries a token issued by a previous server step. `ConfirmationTokens` issues an encrypted token (APP_KEY) bound to the user, a scope (`bulk:<table>:<action>`, `action:<METHOD>:<path>`) and the exact payload (sorted ids, or the filter for "all matching"; never ids for the filter), valid 10 minutes, single use (nonce remembered in the cache). Without a valid token (missing, expired, tampered, other user, action or selection, reused) a bulk request returns the confirmation page: action, number of affected rows and, for "all matching", the active filter; its Confirm button posts the same fields plus the token. With JS the same endpoint answers JSON (`Accept: application/json`) and the existing `<x-codeart::confirm>` modal (bulk: one dialog in the table) shows the texts, then submits the confirmed request. Permissions are checked before any token is issued (403). Row actions and the confirm component post to core's `codeart.confirm` step, never to the target: the target and texts are HMAC-signed so the page cannot be pointed elsewhere, and the target route must carry the `codeart.confirmed` middleware (`RequireConfirmation`), which refuses a request without a fresh token for that user, method and path. Non-destructive bulk actions are unchanged. No `window.confirm` anywhere (a test checks the sources and the built script).

- **US6. Role change has its own route** (`PUT users/{id}/role`, dangerous) so the generic update can never carry a role; `UpdateUser` reads only name, email and role.
- **US7. Password re-confirmation order.** `password.confirm` runs before `codeart.confirmed`, so a missing password confirmation does not spend the confirmation token; after confirming the password the user repeats the action (Laravel returns to the previous page).
- **US8. Bulk restore is not offered**: bulk actions rebuild the query without trashed rows; restore is a row action and on the edit screen.

- **US9. Invitation message is a column** (`user_invitations.message`, 500 chars, shown in the mail only). The invite form also asks for a name, because the mail greets by name and the account is created with it.
- **US10. `StaffUser` contract.** The app's User now implements `Codeart\Core\Auth\Contracts\StaffUser` (the `AdminUser` trait provides every method) so core can use soft deletes, roles and 2FA state with real types; `Admin::staff($model)` narrows a model and fails loudly if the contract is missing.
- **US11. Profile preferences storage.** Reuses `users.locale` and `users.theme_preference`; the latter became nullable (NULL = not chosen, `auto` is a real choice), migration `make_theme_preference_optional_on_users_table`. The saved choice wins over the browser's localStorage so the same person sees the same theme on every device; guests and users without a choice keep the browser/site default. The user-menu switcher saves best effort (fetch, no error shown).
- **US12. Not done in step 4 (open):** avatar upload (needs ImageProcessor + image field wiring), active-sessions list (excluded by the brief). Profile edits cannot change e-mail by design.
