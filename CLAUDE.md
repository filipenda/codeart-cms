# CodeArt CMS

Modular, reusable Laravel CMS: one shared codebase (core + modules) installed separately on many client servers (cPanel; sometimes SSH, sometimes FTP only). The CMS never dictates how the client's public website looks. Only a super-admin can enable/disable modules. Content is multilingual (sr Latin source, sr-Cyrl generated with manual override, en by hand); see "Translations" below.

## Structure (monorepo, released later as split packages)
- `packages/core`      `codeart/core`: Laravel package, auto-discovery, tokens, theme, contracts, events
- `packages/modules/`  future `codeart/module-<name>`
- `apps/starter`       thin Laravel 13 app requiring core via Composer `path` repositories
- `tools/`             repo tooling (`check-colors.php`); `docs/` decisions and task briefs

Env: PHP >= 8.4 (composer `platform` 8.4.1, CI on 8.4 and latest stable), Laravel 13, DDEV (PHP 8.5, MariaDB 12.3). Dev and tests run on MariaDB (database `db` for dev, `test` for tests, created by a DDEV post-start hook), never SQLite. Always build on the latest stable versions; see "Hosting requirements" in docs/ARCHITECTURE.md. No Node on production: assets are built locally and shipped inside packages. No queue workers: database queue + scheduler via cron.

## Commands
- `ddev start`, then `ddev composer setup` (first time)
- `ddev composer check:fast` = check:colors + Pint + Larastan + only the tests affected by the change (`tools/affected-tests.php`); `ddev composer check` = full run + Pint (test mode) + Larastan + Pest for core and starter
- `ddev composer check:colors` alone; inside a package: `composer check`, `composer test`
- Rebuild CSS and JS: `ddev exec "cd packages/core && npm run build"` (commit `resources/dist`)

## Code conventions
- Thin controllers/Livewire components -> Action classes (one class = one operation) -> Eloquent models.
- Service classes only when several actions share logic. No generic repository layer over Eloquent; interface + adapter ONLY for external systems (ERP etc.).
- Modules never call each other directly: they communicate through events and contracts (interfaces) defined in core.
- Primary key: normal auto-increment ID. Add a ULID column only where an ID is exposed externally (API, public URLs, ERP sync).
- Table prefix per module (e.g. `pages_*`).
- Admin UI (later): Blade + Livewire + Alpine + Tailwind. No React in admin.
- Everything must work on shared hosting over SSH or FTP only: no daemons, no Node, no required root access.

## Color rule (strict)
Every color lives in ONE place: `packages/core/resources/css/tokens.css` (plus brand defaults in `packages/core/config/codeart.php`).
- Views, components, CSS and PHP use only semantic utilities (`bg-primary`, `text-on-primary`, `text-text-muted` ...).
- No hex/rgb/hsl and no raw Tailwind palette colors (`bg-lime-400`, `bg-white`) anywhere else. `composer check:colors` enforces it (tests dirs are not scanned).
- Client colors come from `ThemeSettings` (derives shades, picks readable text by WCAG contrast).

## Modules and permissions
- **New modules are created with the generator**: `php artisan make:module <name> [--translatable=title,body] [--slug] [--publishable=true|false] [--no-widget]` (docs/modules.md, docs/publishing-and-preview.md). Never copy another module by hand. Content modules use core's publishing workflow (drafts, scheduling, preview), not their own.
- A module = Composer package `type: codeart-module` + `module.json` (`docs/modules.md`). Version comes from Composer, never from module.json. Core owns the registry; only enabled modules boot.
- Permissions are `<module>.<action>`; roles `super-admin`/`admin`/`editor` (spatie/laravel-permission); `manage-modules` Gate = super-admin only. Core does not own the User model (the app adds `HasRoles`).

## Translations (content only, not admin UI strings)
- Translatable models use core's `Translatable` trait + a `<Model>Translation` table (one row per locale, `manual_fields` JSON, unique `(locale, slug)`); see "Translations" in `docs/modules.md`.
- `sr` is the source; `sr-Cyrl` is generated by `SerbianLatinToCyrillic` except attributes in `manual_fields`. Never overwrite those; slugs are always lowercase ASCII.
- Locales, enabled list and fallback chain live in `config/codeart.php` (`locales`), DB settings later. Write translations only via `setTranslation()`.

## Settings
- Settings are typed DB values with definitions (`SettingsRegistry`); modules register theirs in their provider (`docs/modules.md`). Read with `Settings::get`; people write through `SettingsManager::update` (permission + lock), code/CLI with `Settings::set`. Unknown keys throw; secrets are encrypted and shown only via `masked()`.
- Colors/locales/theme mode come from settings with config defaults; never read `config('codeart.theme.*')` or `codeart.locales.enabled` directly in app code.

## Authentication (details: docs/auth.md)
- Staff sign in on guard `admin` (Laravel Fortify). Screens are Blade + Alpine in `codeart::auth.*` (no Livewire), forms post straight to Fortify and work without JS. All routes sit under the setting `auth.admin_path`; no `route:cache`. Core does not own `User`: the app's model uses `Codeart\Core\Auth\Concerns\AdminUser`.
- Every admin route uses `['web', 'auth:admin', 'admin.access']`. Roles/permissions are guard `admin`: `super-admin`, `admin`, `editor`, `member`; permissions `admin.access`, `users.view|invite|manage|approve`. Only a super-admin touches a super-admin (`RoleRank`, `UserPolicy`).
- Security behaviour is settings-driven (`security.*`, `auth.*`, `mail.*`); defaults: 2FA required for super-admin/admin, registration OFF. Never log passwords, tokens or codes: write through `ActivityLog::record()`.
- UI strings: edit `resources/lang/{sr,en}`, then run `php artisan lang:transliterate` and commit `sr-Cyrl` (a test checks it).
- UI building blocks: anonymous components `<x-codeart::...>` (`docs/components.md`), only semantic utilities. Rebuild CSS + JS after touching views/CSS/JS: `ddev exec "cd packages/core && npm run build"` and commit `resources/dist`. Screens are overridable with `vendor:publish --tag=codeart-views`.
- First super-admin: `php artisan codeart:roles`, then `php artisan user:create "Name" email super-admin`.

## Admin shell (details: docs/admin-ui.md, docs/modules.md)
- Admin pages use `<x-codeart::admin.layout>`; modules add menu items, dashboard widgets, quick actions and search results from their provider (`AdminMenu`, `WidgetRegistry`, `QuickActions`, `SearchRegistry`). Never link to a page that does not exist, never show invented numbers.
- Icons: Lucide names from `packages/core/scripts/icons.txt` (`npm run build:icons`); font Inter is self-hosted. `npm run build` also copies the fonts.

## Lists (details: docs/components.md "Data table", DECISIONS TB)
- Every list is a `DataTable` definition (registered in `TableRegistry`) rendered by `<x-codeart::table>`: one page per request (25, max 100), state in the query string, exact count, no N+1 (declare `with()`), bulk actions and CSV export in chunks, permissions hidden and enforced. Never load all rows or all ids; slow tables are optimized only after `codeart:bench:table`-style measurement.

## Release rules (short; full text in CONTRIBUTING.md)
`main` = next release, NOT production; nothing deploys from it. Releases are Git tags: `x.y.z-rc.N` only on a test site, `x.y.z` stable for clients (`^x.y`). Hotfix = branch from the released tag; `1.x` maintenance branches only for old lines. Client app repos differ: PR -> staging -> main = production.

## Workflow (details: CONTRIBUTING.md, DECISIONS W1-W8)
- `main` holds only finished, working features (a whole module), never half-done pieces. One branch per feature (`feat/admin-ui`); several sessions may add commits to it.
- While working: run only `ddev composer check:fast`; no CI, no PR. Commit and push the branch (push is fine), then report.
- Open a PR, wait for CI and merge ONLY when the prompt says "finish the feature": then run full `ddev composer check` once, CI once, squash-merge on green.
- W7: commit only after `check:fast` passes; a failing check is investigated, never skipped or committed over; a flaky test is fixed at the root, not retried.
- W8: the last step of every task is to leave the local dev environment ready to open in the browser (`ddev composer install`, `migrate`, `codeart:roles`, publish assets, `optimize:clear`) and say so in the report; the owner never runs setup commands by hand. Automated HTTP checks must not leave rows in the dev `sessions` table (use `SESSION_DRIVER=array` or delete what they created).
- After merging to main, also wait for the push run on main (`gh run list --branch main --limit 1`, `gh run watch`) and report it; if red, fix it before any other work (W6).
- Version tags only when a feature set is stable. Every task brief states its branch and whether it finishes the feature.

## Git rules
- `main` is always releasable; short-lived branches `feat/`, `fix/`, `chore/`; Conventional Commits; PRs are squash-merged.
- Never push or touch `main` unless asked. CI is informational (no branch protection), see CONTRIBUTING.md.

## Verification rule
Never take screenshots. Verify front-end work by measuring: rendered HTML, CSS text, computed/derived values and contrast ratios in Pest tests.
Do not read `vendor/` or `node_modules/`.

## Installer (details: docs/install.md, docs/client/instalacija.md)
- One `InstallerService` for the wizard (`/install`) and `codeart:install`; installed = marker `storage/app/installed`; the wizard exists only where `install.key` exists (client ZIP, built by `tools/build-package.php`, never committed).
- Preview the wizard in a browser: `ddev composer preview:install` (URL + key printed, dev `.env`/DB untouched), remove with `ddev composer preview:install:clean`.
- Install tests and checks never touch the dev `.env` or the dev database: they use a temporary directory and a throwaway database (`InstallTestCase`).
